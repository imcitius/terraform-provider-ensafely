# ensafely_check (Resource)

Manages one Check. Each check has common settings and **exactly one** type
block: `http`, `tcp`, `icmp`, `dns`, `ssl_cert`, `domain_expiry`, `passive`,
`pgsql_query`, `mysql_query`, `redis`, `mongodb`, `ssh`, `smtp`, `grpc_health`
or `websocket`.
Changing the type block replaces the check; other changes are in place.

**Inheritance.** `interval`, `severity`, `alert_channels`, `re_alert_interval`,
`retry_count`, `retry_interval` and `escalation_policy` are optional and never
computed. Leave them null to use the Tenant's check defaults: the provider does
not copy effective values into state, so changing the check defaults causes no
diff on such checks.

**Identity.** The provider generates the check UUID and sends it on create, so
a retried create does not make a second check. `id` is the UUID.

**Secrets.** Inline secrets are write-only (`<field>_wo`, Terraform 1.11+) and
never stored in plan or state: the HTTP basic-auth password and request headers,
the `password_wo` of `pgsql_query`, `mysql_query`, `redis` and `smtp`, and the
whole MongoDB URI (`mongodb.uri_wo`). A secret is sent on
create and, afterwards, only when its `<field>_wo_version` changes. Removing the
value and changing the version clears the stored secret. Changes made outside
Terraform to secret values are not detected.

**Connections.** Instead of inline credentials, `http`, `pgsql_query`,
`mysql_query` and `mongodb` checks can set `connection_id` to an
[`ensafely_connection`](connection.md) of the matching type (`http`,
`postgres`, `mysql`, `mongo`). The Connection supplies host, port and
credentials when the check runs, so `host` (`http.url`, `mongodb.uri_wo`) is
then optional. Setting `connection_id` together with an inline credential
(`username`, `basic_auth_user`, `password_wo`, `basic_auth_password_wo`,
`uri_wo`) is a validation error, and inline credential secrets stored earlier
are cleared. Other check types reject `connection_id`. Removing
`connection_id` removes the reference and sends the configured inline secrets
again, without a version change.

## Example usage

```terraform
resource "ensafely_check" "api" {
  name     = "Public API"
  project  = "production"
  group    = "api"
  interval = "1m"
  # Null inheritable fields (severity, alert_channels, retry_count, ...)
  # use the Tenant's check defaults.

  http {
    url          = "https://api.example.com/health"
    status_codes = [200]
    answer       = "ok"

    basic_auth_user                = "monitor"
    basic_auth_password_wo         = var.monitor_password
    basic_auth_password_wo_version = 1
  }
}

# Host and credentials come from a Connection instead of inline secrets.
resource "ensafely_connection" "orders_db" {
  name                = "orders-db"
  type                = "postgres"
  host                = "orders-db.internal"
  username            = "monitor"
  password_wo         = var.orders_db_password
  password_wo_version = 1
  params = {
    db_name = "orders"
  }
}

resource "ensafely_check" "orders_db" {
  name          = "Orders database"
  project       = "production"
  connection_id = ensafely_connection.orders_db.id

  pgsql_query {
    query    = "SELECT count(*) > 0 FROM orders"
    response = "true"
  }
}

resource "ensafely_check" "heartbeat" {
  name    = "Nightly backup"
  project = "production"

  passive {
    timeout = "25h"
  }
}
```

## Import

```shell
terraform import ensafely_check.api 123e4567-e89b-12d3-a456-426614174000
```

Secrets and their `_wo_version` numbers cannot be read back; set the versions
in configuration after import (a version change sends the configured secret).
`terraform plan -generate-config-out` works for existing checks.
